 Donora+ Development Plan Practical roadmap from project setup to tested MVP deployment Basis: Donora+ Product Requirements Document (Version 1.0, August 2026) and the previously prepared System Architecture Document. The PRD defines a three-person team, a hackathon-focused MVP, and a deliberately minimal six-day build strategy. The plan below converts those requirements into executable development work. 1. Development Objective The primary objective is not to build every future Donora+ feature. It is to produce a stable, demoable, end-to-end MVP in which a donor can register and become verified, a seeker can create a blood request, compatible eligible donors can be discovered on a map, both parties can initiate chat, and push notifications work on real devices. The PRD explicitly defines the MVP around this complete flow rather than feature depth. fileciteturn1file3L592-L618 2. Guiding Development Principles Build the end-to-end critical path first; do not polish isolated screens before the core flow works. Keep Supabase as the primary backend. Use Firebase only for Cloud Messaging, avoiding duplicate application data. Keep the AI chatbot replaceable and independent from the core matching/chat workflow. Enforce verification, cooldown, authorization and eligibility on the backend, not only in Flutter. Use a shared Flutter component/style baseline so beginner contributors can build consistently. Do not add deferred features simply because they are technically interesting. Test every completed feature immediately instead of leaving integration and bug fixing until the final day. These priorities directly address the PRD's identified risks: two beginner Flutter contributors, uncertain Alibaba Cloud AI availability, Firebase/Supabase integration complexity, and the tight six-day schedule. fileciteturn1file1L94-L152 3. MVP Scope Lock The MVP must include: Email/phone authentication through Supabase Auth. Single account with seeker/donor role switching. Donor profile with blood group, city, health disclosure and hemoglobin fields. Volunteer / Compensated for travel &amp; time classification. CNIC front + back and live selfie upload. Manual admin approve/reject verification. Automatic three-month donation cooldown. City-level donor/request matching with blood-group filtering. Role-specific map views. Basic 1-to-1 text chat. FCM push notifications for matches and messages. Lightweight Alibaba Cloud AI chatbot for guided request creation. Admin panel for verification and user/flag management. Urgent and top-donor boolean flags. These are the PRD's defined MVP implementations. fileciteturn1file7L592-L618 6. Explicitly Deferred Payment gateway or in-app compensation. Automated CNIC authenticity, face matching or biometric liveness. Clinical validation of hemoglobin or health information. Voice/video calling. Blood-bank or hospital inventory integration. Donor ratings/reviews. Multi-language localization beyond the initial launch language. Advanced automated donor ranking beyond city + blood-group filtering. Seeker/donor web application; only the admin panel is web-based in MVP. These are explicitly deferred by the PRD and should not enter the sprint unless all P0/P1 work is complete. fileciteturn1file2L217-L227 7. Phase 0 — Project Setup Goal: eliminate setup uncertainty before feature development. Create/confirm GitHub repository and branch strategy. Create Flutter project and lock Flutter/Dart versions. Create Supabase development project. Create production Supabase project or reserve it for release. Create Firebase project and configure Cloud Messaging. Create Google Maps credentials/restrictions. Confirm Alibaba Cloud AI tool/model and API access. Create admin web project. Create .env / secret management approach; never commit secrets. Define development, staging/demo and production configurations. Create README with setup instructions. Definition of Done — Setup Every team member can clone the repositories and run the mobile app. Flutter builds successfully on the target test devices. Supabase connection works from development. Firebase FCM test notification is received on at least one real device. Admin dashboard runs locally. All required environment variables are documented without exposing secrets. 9. Phase 1 — Database &amp; Backend Foundation Goal: create the data model and security foundation before UI depends on it. Create profiles/users data structure. Create donor profile fields. Create blood requests. Create matches. Create conversations and messages. Create verification records. Create notifications and device token records. Add status enums/constraints. Add created_at/updated_at fields where needed. Add indexes for blood group, city, availability, request status and conversation IDs. Create RLS policies for user-owned data. Create admin-only access paths. Backend Rules to Implement Early A user can update only their own profile. A donor cannot approve their own verification. Verification status can only be changed through authorized admin logic. Private CNIC/selfie files are never public. Users can only access conversations in which they participate. Suspended users cannot participate in matching/chat. Definition of Done — Backend Foundation Schema can be recreated from migrations/scripts. RLS is enabled on all user-facing tables. Seed/test users can be created. A basic authenticated CRUD operation works from Flutter. Admin access is separated from normal user access. 10. Phase 2 — Authentication, Profiles &amp; Roles Goal: establish the identity and role system used by every subsequent feature. Build sign-up/login. Implement session persistence. Create profile onboarding. Implement seeker/donor role switch. Collect blood group, city, donor classification and health fields. Implement logout/session expiry handling. Add validation and loading/error states. Definition of Done — Auth A new user can register and log in. Session survives app restart. The same account can switch roles without creating another account. Invalid credentials and network failures show useful errors. Unauthorized screens cannot be accessed. The PRD requires email/phone authentication and role switching through Supabase Auth. fileciteturn1file4L347-L355 11. Phase 3 — Donor Verification &amp; Admin Panel Goal: make verified donor discovery trustworthy enough for the MVP. Build guided CNIC front upload. Build CNIC back upload. Build live selfie capture/upload. Store files in private Supabase Storage buckets. Create pending verification record. Build admin verification queue. Display submitted images securely to admin. Implement approve/reject actions. Implement rejection reason. Allow rejected users to resubmit. Notify donor when status changes. Only approved donors become eligible for matching. Definition of Done — Verification A donor can submit all three required images. Admin sees the submission as pending. Admin can approve or reject it. Rejected users can resubmit. Approved donor status is reflected in the app without reinstalling. Sensitive files remain private. The PRD requires manual CNIC/selfie verification and explicitly excludes automated ID/face matching from MVP. fileciteturn1file4L352-L355 12. Phase 4 — Eligibility &amp; Donation Cooldown Goal: prevent ineligible donors from appearing in active matching. Add last_donation_date. Implement three-month cooldown calculation server-side. Create an eligibility condition used by matching queries. Allow eligible donor to reappear automatically after cooldown. Show donor's eligibility/availability state in their own profile. Test dates around the exact three-month boundary. Definition of Done — Cooldown A donor inside the cooldown is absent from matching results. A donor whose cooldown has expired appears without admin action. Changing the last donation date updates eligibility correctly. Boundary-date tests pass. The PRD specifically requires automatic three-month exclusion and automatic reappearance. fileciteturn1file4L356-L359 13. Phase 5 — Blood Requests &amp; Matching Goal: build the central Donora+ value proposition. Create blood request form. Collect blood group, city, urgency and notes. Validate required fields. Store active request. Implement city-level filtering. Implement blood-group compatibility/filtering. Exclude unverified donors. Exclude unavailable/suspended donors. Exclude donors in cooldown. Return eligible donors ordered by practical proximity or simple deterministic ordering. Allow donor-side view of active requests matching their blood group. Implement request lifecycle: active, matched/responded, completed, cancelled/expired. Definition of Done — Matching A seeker can create an active request. Only compatible, verified, eligible donors appear. Donors outside the selected city are excluded. An ineligible cooldown donor is excluded. Donor can see relevant active requests. No client-side-only eligibility bypass exists. The MVP is intentionally limited to city-level matching and blood-group filtering rather than a complex ranking algorithm. fileciteturn1file7L603-L618 14. Phase 6 — Maps &amp; Location Goal: make matching visually actionable without exposing unnecessary private location data. Request location permission only when needed. Store city and appropriate coordinates. Integrate Google Maps. Create seeker map of compatible donors. Create donor map of matching active requests. Restrict results to the relevant city. Use approximate/appropriate location presentation rather than exposing private residential coordinates. Handle denied location permission gracefully. Definition of Done — Maps Map loads on a real device. Markers correspond to valid matching records. Blood-group filtering updates the map. City restriction works. Location permission denial does not crash the app. 15. Phase 7 — Match Initiation &amp; Chat Goal: complete the core seeker-to-donor interaction. Create match/contact record. Prevent duplicate active matches for the same pair/request where appropriate. Create conversation on match initiation. Build 1-to-1 text chat UI. Subscribe to Supabase Realtime messages. Persist messages in PostgreSQL. Implement sent/received states. Implement basic read state if time allows. Do not expose phone number automatically. Definition of Done — Chat Seeker can initiate chat with a valid donor. Donor can receive and reply. Messages persist after app restart. Realtime messages appear without manual refresh. Users cannot read conversations they do not belong to. The PRD defines the MVP communication layer as basic in-app 1-to-1 text chat. fileciteturn1file3L277-L285 16. Phase 8 — Firebase Cloud Messaging Goal: make important events visible even when the app is not open. Register FCM device token after authentication. Store token in Supabase; do not duplicate user/application data in Firebase. Implement server-side notification function. Send match notification. Send new message notification. Send verification result notification. Handle foreground notification. Handle background/tap navigation. Support token refresh. Definition of Done — Notifications Notification reaches a real device within seconds under normal conditions. Tapping notification opens the correct screen/context. Expired/invalid tokens are handled. No private medical or identity data is unnecessarily exposed in notification text. The PRD explicitly scopes Firebase to Cloud Messaging and requires real-device notification testing. fileciteturn1file1L133-L143 17. Phase 9 — Alibaba Cloud AI Chatbot Goal: add AI value without putting the core MVP at risk. Confirm Alibaba Cloud AI/Qwen API and rate limits. Create a secure Edge Function AI gateway. Never expose AI API credentials in Flutter. Define a narrow prompt for blood-request assistance. Extract/suggest only structured request fields: blood group, city, urgency and notes. Return structured data or clearly separated suggestions. Let user review and confirm before submission. Add basic failure/fallback state. Keep chatbot independent from matching and chat. Definition of Done — AI User can ask the assistant for help creating a request. Assistant suggests request fields. User remains in control and can edit values. AI failure does not block manual request creation. Secrets are server-side only. The PRD requires the chatbot to assist with request creation and explicitly says its output should populate/suggest values rather than replace the request form. fileciteturn1file4L369-L371 18. Daily Development Rhythm Start of day: 10-minute task sync and dependency check. Work in small branches; merge completed slices rather than large unfinished branches. Before merging: run analyzer/tests relevant to the changed feature. After merging: one teammate performs a quick integration smoke test. End of day: update task status, record blockers and prepare the next day's highest-priority tasks. Do not wait until Day 6 to discover that two modules do not integrate. 21. Testing Strategy 21.1 Unit Tests Three-month cooldown calculation. Blood-group compatibility/filtering. Request status transitions. Role/permission checks where practical. Validation of request payloads. 21.2 Widget/UI Tests Login form validation. Role switch. Donor verification upload states. Blood request form. Chat message rendering. Notification navigation. 21.3 Integration Tests Auth → profile creation. Donor → verification submission → admin approval. Admin approval → donor appears in matching. Cooldown → donor disappears from matching. Request → match → chat. Chat/message → FCM notification. AI suggestion → request form. 21.4 Real-Device Tests At least one Android physical device for FCM. Bug-Fixing Process Severity Definition Action P0 Crash, security issue, data leak, auth bypass, core demo flow blocked Fix immediately; no release until resolved P1 Core feature broken but workaround exists Fix before final demo P2 Minor functional/UI issue Fix after P0/P1; may ship if low risk P3 Cosmetic/nice-to-have Defer unless time remains Every bug report should contain: Device/environment. Steps to reproduce. Expected result. Actual result. Screenshot/video if useful. Severity. Relevant logs/error message. 24. Security QA Checklist No Supabase service-role key in Flutter. No Alibaba Cloud API secret in Flutter. Private CNIC/selfie storage cannot be accessed anonymously. RLS is enabled and tested. Users cannot edit another user's profile. Users cannot access another user's private conversation. Only admins can approve verification. Suspended users cannot perform protected actions. Push payloads do not contain unnecessary sensitive information. Exact donor location is not unnecessarily exposed. 25. Performance &amp; Reliability Checklist Avoid unnecessary full-table queries. Use pagination for lists. Index frequently filtered fields. Do not load all donor/request records into Flutter. Show loading states for network operations. Show retry states for failed network operations. Prevent duplicate submissions with disabled buttons/idempotent backend operations. Handle offline/poor-network conditions gracefully. Dispose realtime subscriptions when screens are removed. 26. Deployment Plan 26.1 Development Development Supabase project. Debug Flutter build. Test Firebase credentials. Test admin locally. 26.2 Demo/Staging Seed safe demo accounts. Seed approved donor(s). Seed a controlled blood request scenario. Use real-device FCM. Use production-like configuration without real sensitive personal data. 26.3 Production / Submission Build Run final automated tests. Run the mandatory end-to-end test. Verify environment variables. Verify Supabase RLS. Verify private storage. Verify FCM. Build signed Android/iOS artifacts as applicable. Deploy admin panel. Tag the Git commit used for the final demo. 27. Release Gate Do not call the MVP complete until all of the following are true: Authentication works on a real device. Role switching works. Donor verification works end-to-end. Admin approval/rejection works. Cooldown is enforced automatically. Seeker can create a request. Compatible verified donors appear correctly. Maps work. Seeker and donor can chat. FCM notification works on a real device. AI assistant works or a clearly tested fallback preserves manual request creation. Admin changes propagate to the app. No P0 bugs remain. No known critical security issue remains. The full demo can be completed from clean test accounts without manual database manipulation during the presentation. 28. Definition of Done — Universal A development task is considered Done only when: The implementation satisfies its acceptance criteria. The feature works from the actual UI, not only from a database/API test. Loading, success and failure states are handled. Authorization/security rules are enforced server-side where applicable. Data persists correctly after app restart. Relevant unit/widget/integration tests pass. The feature has been tested on the target device/environment. No new analyzer/build errors are introduced. The branch is merged cleanly into the shared development branch. The feature has been smoke-tested with at least one dependent feature. The feature-specific acceptance criteria come from the PRD, including authentication/roles, verification, cooldown, matching/maps, chat/notifications, AI and admin behavior. fileciteturn1file4L347-L375 29.
