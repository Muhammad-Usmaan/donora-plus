Introduction &amp; Scope 1.1 Purpose This Software Requirements Specification (SRS) defines every functional and non-functional requirement for Donora+, a mobile-first blood donation matching platform. It serves as the single source of truth for all build decisions during the hackathon and for any post-hackathon continuation. Every requirement is written to be independently testable. 1.2 Problem Statement In Pakistan, urgent blood requests are routed through social media influencers because no structured channel exists. This system fails when a post doesn&apos;t go viral, when the influencer is unreachable, or when donors cannot be verified. Donora+ replaces viral dependency with a structured, city-scoped, verified donor network and real-time matching. 1.3 Scope — MVP Mobile app (Flutter) for Seekers and Donors on Android and iOS. Web admin panel for internal verification and moderation. Backend: Supabase (Postgres, Auth, Storage, Realtime). Push: Firebase Cloud Messaging. AI: Alibaba Cloud (Qwen model). City-scoped matching, identity verification, in-app chat, push notifications, AI chatbot, and a 3-month donation cooldown. No payment processing. No hospital-system integration. No automated ID/face verification. 1.4 Priority Convention Priority Meaning MVP Required? MUST Non-negotiable. App cannot ship without this. Yes SHOULD High business value. Implement if sprint capacity allows. Conditional MAY Post-hackathon roadmap item. Documented here for future reference. No 1.5 Definitions Term Definition Seeker A user who has posted or needs to post a blood donation request. Donor A verified user who is eligible and willing to donate blood. Admin An internal team member who reviews verifications and manages users via the web panel. Cooldown The 90-day minimum period between a donor&apos;s consecutive donations, enforced by the system. Verification The process of submitting and approving CNIC front/back photos and a live selfie to confirm a donor&apos;s identity. Classification A donor&apos;s self-declared compensation preference: Volunteer or Compensated for travel &amp; time. Urgent Badge An admin-toggled flag that surfaces a request above standard listings and adds a visual pulse indicator. Top Donor An admin-toggled flag that increases a donor&apos;s visibility in search results. FCM Firebase Cloud Messaging — the push notification delivery service. RLS Row-Level Security — Postgres/Supabase policy layer that enforces data access rules at the database level. CNIC Computerised National Identity Card — Pakistan&apos;s national identity document. OTP One-Time Password — a time-limited numeric code sent to verify ownership of a phone number or email. 2. User Roles &amp; Permissions Donora+ has three roles. Authentication &amp; Authorization FR-AUTH-001 User Registration [MUST] Any visitor may create a Donora+ account using a Pakistani phone number or email address. Requirements: System accepts phone (+92 prefix, 10 digits) OR email as the primary identifier. Required fields: full name, identifier (phone/email), password, password confirmation, and initial role selection (Seeker / Donor). Password must be at least 8 characters, contain at least one digit, and at least one special character. System prevents duplicate registration: if the phone/email already exists, registration is rejected with a descriptive error. Successful registration immediately triggers OTP delivery (FR-AUTH-002) and does NOT grant full session access until OTP is verified. Initial role selection persists as the user&apos;s default active role but does not restrict role switching later. Acceptance criteria: GIVEN a visitor submits a valid name, phone, and password WHEN registration is called THEN a new user row is created in auth.users with email_confirmed_at = NULL and an OTP is sent. GIVEN phone &apos;+923001234567&apos; already exists WHEN a new registration uses the same number THEN the API returns HTTP 409 and no new user row is created. GIVEN a password of &apos;12345678&apos; (no special character) WHEN submitted THEN client-side and server-side validation both reject it with a specific error message. GIVEN a duplicate email WHEN re-registered THEN the system returns &apos;An account with this email already exists&apos; and does not expose whether the existing account is active. Do not collect blood group or city at registration. These are collected during onboarding to reduce friction at the top of the funnel. FR-AUTH-002 OTP Verification [MUST] After registration or phone-change, the system sends a 6-digit OTP and verifies it before granting full access. Requirements: OTP is exactly 6 numeric digits. OTP expires after 10 minutes from issuance. Maximum 5 incorrect attempts before the OTP is invalidated; user must request a new code. Resend is rate-limited: maximum 3 resend requests per phone/email per 60 minutes. Verified OTP sets email_confirmed_at on the user record and creates the full app session. Acceptance criteria: GIVEN a valid OTP WHEN entered within 10 minutes THEN the session is established and user is redirected to Onboarding. GIVEN an expired OTP WHEN entered THEN the system returns &apos;Code expired. Request a new one.&apos; and does not grant access. GIVEN 5 consecutive wrong entries WHEN a 6th is attempted THEN the OTP is invalidated and user must request a fresh code. GIVEN 3 resend requests in 60 minutes WHEN a 4th is requested THEN the system returns &apos;Too many attempts. Try again in X minutes.&apos; FR-AUTH-003 Login [MUST] Registered and verified users can log in with their phone/email and password. Requirements: Login accepts phone OR email plus password. Failed login increments a lockout counter; after 10 consecutive failures the account is locked for 15 minutes. Lockout is scoped per account (not per IP) so legitimate users on the same network are unaffected. Successful login returns a JWT access token (15-minute expiry) and a refresh token (30-day expiry). Unverified accounts (OTP not completed) are rejected at login with a prompt to complete verification. Acceptance criteria: GIVEN valid credentials WHEN login is submitted THEN an access token and refresh token are returned and the user is navigated to Home. GIVEN wrong password submitted 10 times WHEN an 11th attempt occurs within the window THEN login is blocked for 15 minutes and the user sees the remaining lockout time. GIVEN an unverified account WHEN login is attempted THEN the response is &apos;Please verify your phone number first&apos; with a resend OTP option. FR-AUTH-004 Session &amp; Token Management [MUST] Access tokens are short-lived and silently refreshed; sessions persist across app restarts. Requirements: Access token TTL: 15 minutes. Refresh token TTL: 30 days. App silently refreshes the access token using the refresh token before expiry — no visible re-login prompt during normal use. If the refresh token is expired or revoked, the user is redirected to Login and shown &apos;Your session has expired. Please log in again.&apos; Logging out invalidates the refresh token server-side and clears all local token storage. Admin sessions use the same Supabase Auth mechanism but are scoped to the admin panel web app only. Acceptance criteria: GIVEN an active session WHEN the access token expires THEN the app silently obtains a new token without user interaction. GIVEN a refresh token older than 30 days WHEN the app is opened THEN the user is redirected to Login. GIVEN a user logs out WHEN the old refresh token is submitted THEN Supabase rejects it with 401. FR-AUTH-005 Password Reset [MUST] Users can reset a forgotten password via OTP sent to their registered phone/email. Requirements: Reset flow: enter identifier → receive OTP → enter OTP → enter and confirm new password → session established. Reset OTP expires in 10 minutes and is single-use. New password must meet the same complexity rules as registration. All existing refresh tokens for the account are revoked upon successful reset. Acceptance criteria: GIVEN a valid identifier WHEN reset is initiated THEN an OTP is sent within 60 seconds. GIVEN a reset OTP WHEN used successfully THEN all prior refresh tokens for the account are rejected on the next use. FR-AUTH-006 Role Switching [MUST] Users can switch their active role between Seeker and Donor from the Profile screen without logging out. Requirements: Role switch updates active_role in the profiles table. After switch, bottom navigation tabs, Home screen content, and map view all update immediately to reflect the new role. If the user is in an active chat when switching roles, the chat is not interrupted. The switch does not change any other profile data, permissions, or verification state. If a user switches to Donor and is not yet verified, the app displays the Pending Verification banner on the Donor Home screen. Acceptance criteria: GIVEN a Seeker WHEN role is switched to Donor THEN donor-specific tabs appear, seeker tabs disappear, and active_role in DB reflects &apos;donor&apos;. GIVEN an unverified donor WHEN role switched to Donor THEN Pending Verification banner is displayed and the donor does not appear in seeker searches. 4. Onboarding FR-OB-001 Onboarding Flow [MUST] After OTP verification, new users complete a progressive profile setup before accessing the main app. Requirements: Onboarding consists of 2–4 steps depending on role: Step 1 (Role Confirm) and Step 2 (Profile Basics) apply to all users. Steps 3 (Classification) and 4 (Health Info) apply to Donor role only. Step 2 requires: blood group selection (one of 8 standard types) and city (from the Pakistan city autocomplete list). Profile photo is optional. Step 3 (Donor only): user selects one of two classifications — &apos;Volunteer&apos; or &apos;Compensated for travel &amp; time&apos;. This field is required for donors; it cannot be skipped. Step 4 (Donor only): hemoglobin level (numeric, optional) and health disclosure checklist (at least one option must be selected, including &apos;None of the above&apos;). Users may not skip Step 2 or Step 3 (donor). Step 4 may be skipped with a &apos;Complete later&apos; option; the profile is marked health_info_complete = false. Onboarding is shown exactly once per account. If interrupted and re-opened, the app resumes from the last incomplete step. On completion: Seeker users are navigated to Home. Donor users are navigated to the Verification screen (SCR-D04). Acceptance criteria: GIVEN a new Seeker WHEN onboarding is submitted THEN profiles.blood_group, profiles.city, and profiles.onboarding_complete = true are set and user lands on Seeker Home. GIVEN a new Donor WHEN Step 3 is skipped THEN the form rejects the skip and requires classification selection before proceeding. GIVEN onboarding interrupted at Step 2 WHEN app re-opened THEN user is returned to Step 2, not Step 1. GIVEN a Donor who skipped Step 4 WHEN profile is fetched THEN health_info_complete = false. 5. Donor Verification FR-VER-001 Verification Document Submission [MUST] Donors submit CNIC front, CNIC back, and a live selfie for identity verification. Requirements: Three assets are required: CNIC front photo, CNIC back photo, and live selfie. All three must be submitted together in one flow. CNIC images may be uploaded from the device gallery or captured via camera. Selfie must be captured live using the front-facing camera; gallery upload is not permitted for the selfie step. Each image must be under 5 MB. Accepted formats: JPEG, PNG. Images are uploaded to a private Supabase Storage bucket (verifications/) accessible only to the submitting user (for upload) and admins (for review). After upload, a row is inserted in verification_submissions with status = &apos;pending&apos;, user_id, file URLs, and submitted_at timestamp. A user may only have one active submission (status = pending or approved). A rejected submission unlocks a new submission. The donor&apos;s account remains in Pending state (invisible to seekers) until an admin approves the submission. Acceptance criteria: GIVEN all three assets uploaded WHEN &apos;Submit for Review&apos; is tapped THEN verification_submissions row is created with status=&apos;pending&apos; and three non-null file URLs. GIVEN a selfie image selected from gallery WHEN the step is reached THEN the gallery option is disabled; only camera capture is available. GIVEN an image of 6 MB WHEN upload is attempted THEN the client rejects it before upload with &apos;File exceeds 5 MB limit&apos;. GIVEN a donor with status=&apos;approved&apos; WHEN they visit the Verification screen THEN the upload form is replaced with an &apos;Approved&apos; status card. GIVEN a donor with status=&apos;pending&apos; WHEN they re-enter the Verification screen THEN the upload form is replaced with a &apos;Pending Review&apos; status card; resubmission is not possible. The selfie camera-only restriction prevents CNIC photos from being re-submitted as selfies. FR-VER-002 Admin Verification Review [MUST] Admins can view, approve, or reject donor verification submissions from the web admin panel. Requirements: Admin panel displays all submissions sortable by submitted_at. Default sort: oldest pending first. Each submission shows: user&apos;s name, phone, blood group, city, CNIC front, CNIC back, and selfie — all in one view without page navigation. Admin can Approve: sets verification_submissions.status = &apos;approved&apos;, sets profiles.is_verified = true, and triggers a push notification to the donor. Admin can Reject: requires a non-empty rejection reason (max 500 characters). Sets status = &apos;rejected&apos;, stores rejection_reason, triggers push notification to donor with the reason. Approval and rejection are logged in admin_audit_log with admin_id, action, target_user_id, and timestamp. Admin cannot view CNIC images of any user other than through the verification submission workflow. Acceptance criteria: GIVEN a pending submission WHEN admin clicks Approve THEN profiles.is_verified = true, submission status = &apos;approved&apos;, donor receives push notification &apos;Your account has been verified&apos;. GIVEN admin clicks Reject without entering a reason THEN the Reject button remains disabled. GIVEN a rejection WHEN the donor opens the app THEN the Verification screen shows the rejection reason and a &apos;Resubmit&apos; button. GIVEN any approval or rejection THEN an admin_audit_log row is created with the correct admin_id and timestamp. FR-VER-003 Verification Status Display [MUST] Users can see their current verification status at all times within the app. Requirements: Verification status is displayed on the Donor Home screen and Profile screen as a chip: Not Submitted (grey) / Pending (amber) / Approved (teal) / Rejected (red). Rejected status includes the rejection reason visible to the donor in the app. Approved donors display a Verified badge on their donor card as seen by seekers. Acceptance criteria: GIVEN a verified donor&apos;s card in the seeker map view THEN a Verified badge (check_circle icon + &apos;Verified&apos; label) is displayed. GIVEN a rejected donor WHEN they view Profile THEN status chip is red and tapping it shows the rejection reason. 6. Blood Donation Matching FR-MATCH-001 Post a Blood Request [MUST] Seekers (and donors acting as seekers) can post a blood donation request that notifies matching donors. Requirements: Required fields: blood_group (one of 8 standard types), units_needed (integer 1–10), hospital_name (string, max 120 chars), city (Pakistan city list). Optional fields: notes (max 300 chars), is_urgent (boolean, default false). is_urgent can be set to true only by: (a) the admin toggling it in the admin panel, OR (b) the seeker requesting it — but the badge only displays after admin confirmation. For MVP, seekers can flag as urgent; admin visibility is immediate. On submission, a blood_requests row is created with status = &apos;active&apos;, requester_id, all fields, and created_at. After creation, all verified donors in the same city whose blood group matches AND who are eligible (not in cooldown) receive a push notification. Push payload includes: request_id, blood_group, hospital_name, city, is_urgent. A seeker may have a maximum of 3 simultaneously active requests. Acceptance criteria: GIVEN valid fields WHEN request is submitted THEN blood_requests row created with status=&apos;active&apos; and push notifications dispatched to matching donors within 10 seconds. GIVEN a seeker already has 3 active requests WHEN a 4th is attempted THEN submission is rejected with &apos;You already have 3 active requests. Please cancel one first.&apos; GIVEN units_needed = 0 WHEN submitted THEN validation rejects with &apos;Units must be between 1 and 10&apos;. GIVEN city = &apos;Karachi&apos; WHEN request is posted THEN only donors whose profiles.city = &apos;Karachi&apos; receive the notification. FR-MATCH-002 Donor Discovery [MUST] Seekers can view nearby verified, eligible donors on a map and in list view, filtered by blood group. Requirements: Donor query criteria for appearing in seeker discovery: is_verified = true AND is_suspended = false AND (last_donation_date IS NULL OR last_donation_date &lt; NOW() - INTERVAL &apos;90 days&apos;) AND city = seeker&apos;s city. Donors in cooldown are completely hidden from seeker discovery — their profile is not shown, not counted in stats. Map view shows verified donor pins in the seeker&apos;s city. Pin tap opens a DonorPreviewCard with: name, blood group, classification, verified badge. List view (bottom sheet) shows the same donors sorted by blood group match (exact match first) then alphabetically. Blood group filter: seeker can filter by one or more blood groups; default shows all groups. Stats on Home screen (nearby count, available now, my blood group match) must be derived from the same query to ensure consistency. Donor&apos;s exact address is never exposed to seekers; city-level location only. Acceptance criteria: GIVEN a donor in cooldown WHEN a seeker views the map THEN that donor&apos;s pin is absent. GIVEN a pending (unverified) donor WHEN a seeker views the map THEN that donor does not appear. GIVEN seeker city = &apos;Lahore&apos; WHEN map loads THEN all pins shown are for donors whose city = &apos;Lahore&apos;. GIVEN blood group filter set to &apos;O+&apos; WHEN applied THEN only O+ donors appear in both map and list view. FR-MATCH-003 Donation Cooldown Enforcement [MUST] After marking a donation complete, a donor is hidden from matching for exactly 90 days. Requirements: When a donor taps &apos;Mark as Donated&apos; in a chat thread, last_donation_date is set to NOW() in profiles. The system computes eligibility as: last_donation_date IS NULL OR last_donation_date + INTERVAL &apos;90 days&apos; &lt;= NOW(). This check is performed at query time (not stored as a flag) to ensure accuracy. Cooldown remaining days = 90 - DATEDIFF(NOW(), last_donation_date). Displayed on Donor Home and Profile. While in cooldown: donor is hidden from seeker map and discovery, but can still browse requests and use chat. Cooldown does NOT prevent the donor from posting a blood request as a seeker. Cooldown reset: only by recording a new donation (tapping &apos;Mark as Donated&apos; again after the prior cooldown expires). Admin cannot override the cooldown — it is a data integrity rule, not a moderation flag. Acceptance criteria: GIVEN last_donation_date = 60 days ago WHEN seeker discovery query runs THEN donor is excluded from results. GIVEN last_donation_date = 91 days ago WHEN seeker discovery query runs THEN donor is included in results. GIVEN donor marks donation complete THEN last_donation_date = current timestamp (±5 seconds) in DB. GIVEN donor in cooldown WHEN Donor Home loads THEN eligibility card shows &apos;Next eligible: [date]&apos; with correct date. Cooldown is enforced at the database query level via Supabase RLS / server-side filtering, not just the Flutter UI. FR-MATCH-004 Request Lifecycle [MUST] Blood requests move through a defined set of statuses and can be cancelled or fulfilled. Requirements: Request statuses: active → fulfilled | cancelled. No other status transitions are permitted. A seeker can cancel their own active request at any time. Cancellation sets status = &apos;cancelled&apos; and cancelled_at = NOW(). A request is marked fulfilled when the seeker taps &apos;Mark as Fulfilled&apos; on the Request Detail screen. fulfilled_at = NOW(), fulfilled_by_donor_id is set. Cancelled and fulfilled requests are retained in the database for history; they are not deleted. Donors cannot see cancelled or fulfilled requests in their Donate tab. A request automatically expires (status = &apos;expired&apos;) if it remains active for more than 72 hours with no fulfillment. An expired request behaves identically to a cancelled one from the donor&apos;s perspective. Acceptance criteria: GIVEN an active request WHEN seeker taps Cancel THEN status = &apos;cancelled&apos;, cancelled_at is set, and request disappears from the donor&apos;s Donate list within 5 seconds. GIVEN a fulfilled request WHEN a donor views their Donate tab THEN the request does not appear. GIVEN a request active for 73 hours WHEN a scheduled job runs THEN status = &apos;expired&apos; and the request disappears from all donor views. 7. Communication FR-COMM-001 In-App Chat [MUST] Seekers and donors can exchange real-time text messages once a match is initiated, without sharing personal contact details. Requirements: A chat thread is created when a donor taps &apos;I Can Help&apos; on a Request Detail screen. A chat_rooms row is created with seeker_id, donor_id, and request_id. Only one chat room may exist per (seeker_id, donor_id, request_id) triplet. Attempting to create a duplicate navigates to the existing room. Messages are stored in chat_messages with room_id, sender_id, body (text, max 1000 chars), and sent_at. Messages are delivered via Supabase Realtime channel scoped to the chat room. Both participants subscribe on room open. Message delivery confirmation: optimistic UI (message shown immediately at 50% opacity) confirmed when Supabase insert succeeds (full opacity) or failed (red ! retry icon). Neither party&apos;s phone number is automatically shared in chat. Any phone number typed in the message body is sent as-is (not redacted in MVP). Long-press on own messages shows a Delete option. Deletion sets body = &apos;[Message deleted]&apos; and is_deleted = true; the bubble remains but content is replaced. Maximum message length: 1000 characters. Client truncates at character limit; server rejects messages exceeding 1000 chars. Acceptance criteria: GIVEN a donor taps &apos;I Can Help&apos; WHEN no existing room for that triplet exists THEN a new chat_rooms row is created and both users are navigated to the thread. GIVEN a donor taps &apos;I Can Help&apos; WHEN a room already exists for that triplet THEN the existing room is opened; no duplicate row created. GIVEN a message sent while offline WHEN connection restores THEN message is delivered and confirmed without user re-action. GIVEN a message of 1001 characters WHEN send is attempted THEN the server rejects with HTTP 400 and client shows &apos;Message too long&apos;. GIVEN user deletes a message THEN body = &apos;[Message deleted]&apos;, is_deleted = true, and the bubble shows &apos;[Message deleted]&apos; to both participants. FR-COMM-002 Push Notifications [MUST] The app sends push notifications via Firebase Cloud Messaging for key events. Requirements: FCM token is registered on login and updated if the device generates a new token. Notifications are sent for: (a) new blood request matching donor&apos;s blood group and city, (b) donor responds to seeker&apos;s request, (c) new chat message in any active thread, (d) verification approved or rejected. Notification payload must include: notification type, relevant IDs (request_id or room_id), and a human-readable body. Tapping a notification navigates the user directly to the relevant screen (deep link): request detail, chat thread, or verification status. If the app is in the foreground, notifications are shown as in-app banners (not OS notifications) to avoid double-notification. Users can disable notification categories from the Profile &gt; Notifications settings. Preference stored in notification_preferences table. If an FCM token delivery fails (invalid token, app uninstalled), the stale token is removed from the database. Acceptance criteria: GIVEN a matching request is posted WHEN a verified, eligible, city-matched donor is online THEN an FCM push is received within 10 seconds. GIVEN a notification tapped (app closed) WHEN app opens THEN user lands on the correct deep-link screen, not the Home screen. GIVEN user disables &apos;Chat messages&apos; notifications WHEN a chat message is received THEN no push notification is sent; in-app badge still updates. 8. AI Chatbot FR-AI-001 AI Chatbot Integration [MUST] An AI chatbot powered by Alibaba Cloud&apos;s tools assists seekers in creating blood requests and answers basic eligibility questions. Requirements: Chatbot is accessible from: (a) the Seeker Home screen via a dedicated card, (b) an inline &apos;Let AI help me fill this&apos; button on the New Request form. Chatbot is powered by Alibaba Cloud&apos;s AI API (exact endpoint/model to be confirmed at onboarding day). Integration must be swappable behind a service interface so the underlying model can be changed without UI changes. System prompt instructs the chatbot to: identify blood group, city, hospital name, units needed, and urgency. The bot asks one question at a time. When the chatbot has gathered all required request fields, it presents a summary card with a &apos;Use this for my request&apos; button that pre-fills the New Request form. Chatbot conversation is ephemeral — not stored in the database. Each session starts fresh. Chatbot must respond within 8 seconds. If the API does not respond within 8 seconds, the chatbot shows &apos;Taking longer than expected…&apos; and retries once. If the retry fails, an error message is shown with a &apos;Try again&apos; button. Chatbot must not invent medical advice. System prompt must include an explicit instruction: &apos;Do not provide medical advice. If asked, refer the user to a doctor.&apos; Acceptance criteria: GIVEN a seeker opens the chatbot WHEN all required fields are collected THEN a pre-fill summary card is shown with correct field values. GIVEN &apos;Use this for my request&apos; is tapped THEN the New Request form opens with blood_group, hospital_name, city, units_needed, and notes pre-filled from the chatbot. GIVEN the Alibaba Cloud API returns no response within 8 seconds THEN after one retry, the chatbot displays an error message within 16 seconds total. GIVEN the user asks the chatbot for medical advice THEN the chatbot responds with a referral to a doctor and does not provide a medical recommendation. The chatbot integration architecture (service class + interface) must be in place before the exact Alibaba Cloud tool details are confirmed so that integration can be completed in a single sprint once the API credentials are available. 9. Admin Panel The admin panel is a web application (not Flutter). It authenticates admins via Supabase Auth using email/password. Admin accounts must be manually provisioned in Supabase — there is no self-registration for admins. FR-ADM-001 Admin Authentication [MUST] Admin panel has its own login flow restricted to pre-provisioned admin accounts. Requirements: Admin login accepts email and password only (no phone, no OTP for the admin panel). Admin accounts have a role = &apos;admin&apos; claim in their Supabase JWT. All admin panel API calls verify this claim server-side. Failed admin login follows the same lockout rules as user login (10 attempts → 15-minute lockout). Admin sessions timeout after 8 hours of inactivity. Acceptance criteria: GIVEN a non-admin Supabase user WHEN they attempt to call an admin-only API endpoint THEN the call is rejected with HTTP 403. GIVEN an admin session idle for 8 hours WHEN any action is attempted THEN the session is invalidated and the admin is redirected to the admin login screen. FR-ADM-002 Verification Queue [MUST] Admin can view and process all pending donor verification submissions. Requirements: Dashboard stat card shows count of submissions with status = &apos;pending&apos;. Verifications table displays: user name, phone, blood group, city, submitted_at, status. Default sort: oldest pending first. Clicking a pending row opens a detail panel showing all three images (CNIC front, back, selfie) side-by-side with zoom on click. Approve button: enabled always for pending submissions. Reject button: enabled only when rejection_reason field is non-empty. Bulk approval is NOT supported in MVP — each submission is reviewed individually. Admin can filter submissions by status (All / Pending / Approved / Rejected) and search by name or phone. Acceptance criteria: GIVEN 15 pending submissions WHEN admin opens the Verifications page THEN 15 rows appear sorted by oldest submitted_at first. GIVEN admin clicks Approve on a submission THEN profiles.is_verified = true for that user, submission.status = &apos;approved&apos;, and the row moves from Pending to Approved tab. GIVEN rejection reason is empty WHEN Reject is clicked THEN the button is disabled and no action is taken. FR-ADM-003 User Management [MUST] Admin can search, view, edit, and moderate any user account. Requirements: User search by name and/or phone number. Results page: 20 rows with pagination. User detail page shows: all profile fields, verification status, active role, account created date, last login date, flag states, and audit log for that user. Admin can toggle: is_urgent_request (boolean on current active request), is_top_donor (boolean on profiles), is_suspended (boolean on profiles). Admin can edit: name, blood_group, city, donor_classification. Changes are immediately reflected in the app. Suspension (is_suspended = true): the user&apos;s login is not blocked, but the user is hidden from all seeker discovery queries and their active requests are not shown to donors. Security Requirements FR-SEC-001 Data Encryption [MUST] All data in transit and sensitive data at rest must be encrypted. Requirements: All API calls use HTTPS (TLS 1.2+). Plain HTTP is not accepted and should redirect to HTTPS. Supabase Storage: all objects in the verifications/ bucket are private (no public URL). Access is via signed URLs with a 5-minute expiry, generated server-side for admins only. Passwords are never stored in the app or transmitted in plaintext — Supabase Auth handles bcrypt hashing. JWT tokens are stored in Flutter Secure Storage (Keychain on iOS, EncryptedSharedPreferences on Android), not SharedPreferences. Acceptance criteria: GIVEN a direct attempt to access a verification image URL without a valid signed URL THEN Supabase Storage returns HTTP 403. GIVEN the JWT is stored WHEN inspected on a rooted Android device THEN it is stored in EncryptedSharedPreferences, not plaintext SharedPreferences. FR-SEC-002 Row-Level Security [MUST] Supabase RLS policies ensure users can only read and write data they are authorised to access. Requirements: Every table that stores user data has RLS enabled with an explicit DENY ALL default policy. Seeker cannot read another seeker&apos;s request notes — only public fields (blood_group, hospital_name, city, is_urgent, status) are exposed. Donor cannot read another donor&apos;s health_disclosures or hemoglobin_level — these are private fields. Admin role bypasses user RLS but still cannot bypass admin_audit_log immutability constraints. Acceptance criteria: GIVEN RLS is enabled on profiles WHEN an authenticated user queries SELECT * FROM profiles THEN only their own row is returned. GIVEN a donor queries blood_requests THEN requests with status != &apos;active&apos; are excluded from results by RLS. FR-SEC-003 Input Sanitisation [MUST] All user input is sanitised to prevent injection attacks. Requirements: All database writes use Supabase&apos;s parameterised client — no string concatenation in SQL. HTML/script tags in text fields are stripped or escaped before storage. File uploads are validated for MIME type (not just extension) server-side before storage. The AI chatbot system prompt is fixed and prepended server-side — users cannot inject new system instructions through the user message field. Acceptance criteria: GIVEN a message body of &apos;&lt;script&gt;alert(1)&lt;/script&gt;&apos; WHEN inserted THEN the stored value is the escaped string, not executable HTML. FR-SEC-004 Rate Limiting [MUST] All public-facing endpoints are rate-limited to prevent abuse. Requirements: Registration: max 5 attempts per IP per hour. OTP request: max 3 per phone/email per 60 minutes. Login: max 10 attempts per account per 15 minutes (see FR-AUTH-003). Blood request POST: max 10 per user per hour (covers the 3-active-request limit with headroom for create/cancel cycles). Chat message send: max 60 messages per user per minute per room. AI chatbot API: max 20 calls per user per hour. Acceptance criteria: GIVEN 11 login attempts in 15 minutes WHEN the 11th is made THEN HTTP 429 is returned. GIVEN 4 OTP resend requests in 60 minutes WHEN the 4th is attempted THEN HTTP 429 is returned. FR-SEC-005 CNIC &amp; Selfie Privacy [MUST] Identity documents are accessible only to the submitting donor and authorised admins. Requirements: CNIC images are stored in a private Supabase Storage bucket (verifications/) with no public access policy. Signed URLs for CNIC images are generated only by a server-side admin function and expire in 5 minutes. No CNIC image URL is ever returned to the mobile app — only to the admin panel via a protected endpoint. CNIC images are permanently deleted from storage when the user&apos;s account is deleted. Acceptance criteria: GIVEN a mobile app user WHEN they call any API THEN no CNIC image URL is present in any response payload. GIVEN account deletion WHEN storage is inspected THEN no object exists at verifications/{user_id}/. 17.
