 Donora+ System Architecture Document Connecting blood seekers with verified donors — instantly, without relying on social media luck. 1. Document Overview This document defines the recommended technical architecture for Donora+, a mobile blood donation matching platform that connects blood seekers with nearby, verified and potentially eligible blood donors. The architecture is designed to be: Practical for an initial production release Secure enough to handle sensitive identity and health-related information Scalable as the user base grows Simple enough for a small development team to maintain Suitable for real-time donor matching, notifications and communication 1.1 High-Level Architecture ┌─────────────────────────────────────────────┐ │ Mobile Users │ │ Donora+ Flutter Mobile App │ │ Seeker Experience / Donor Experience │ └──────────────────────┬──────────────────────┘ │ HTTPS / Realtime ▼ ┌─────────────────────────────────────────────┐ │ Supabase │ │ Auth • PostgreSQL • Realtime • Storage │ │ Row Level Security • Edge Functions │ └───────┬───────────────┬─────────────────────┘ │ │ ▼ ▼ Firebase FCM External Services Push Notifications Google Maps / Alibaba AI ┌─────────────────────────────────────────────┐ │ Admin Web Dashboard │ │ Next.js / React │ └──────────────────────┬──────────────────────┘ ▼ Supabase 2. Supabase can provide the database, authentication, storage and realtime infrastructure, while Edge Functions handle privileged operations. This keeps the initial system inexpensive and easier to maintain. 3. Frontend Architecture 3.1 Flutter Mobile Application The primary client is a Flutter application targeting Android and iOS. A single account can operate as either a Blood Seeker or Blood Donor and can switch between roles. lib/ ├── core/ │ ├── constants/ │ ├── theme/ │ ├── routing/ │ ├── utils/ │ └── services/ ├── features/ │ ├── auth/ │ ├── profile/ │ ├── donor/ │ ├── seeker/ │ ├── matching/ │ ├── requests/ │ ├── chat/ │ ├── notifications/ │ ├── verification/ │ ├── chatbot/ │ └── settings/ ├── data/ │ ├── models/ │ ├── repositories/ │ └── datasources/ └── main.dart Frontend responsibilities include: UI rendering and navigation Form validation Local state and session handling Map visualization and location permissions Image capture Chat interface Notification handling API communication The frontend should not contain sensitive business rules such as donor medical eligibility, verification authority, donation cooldown enforcement or administrative authorization. Those rules must be enforced on the backend. 4. Backend Architecture Supabase should serve as the primary backend platform. Database Architecture PostgreSQL is recommended because Donora+ has strongly related entities and requires reliable transactional operations. 5.1 Core Tables users id, email, phone, created_at, updated_at, account_status profiles user_id, full_name, date_of_birth, gender, city, profile_image_url, active_role, is_verified, created_at, updated_at donor_profiles user_id, blood_group, hemoglobin_level, health_disclosures, last_donation_date, donation_eligibility, availability_status, latitude, longitude, updated_at blood_requests id, seeker_id, blood_group, required_units, hospital_name, hospital_location, latitude, longitude, urgency, description, status, created_at, expires_at matches id, request_id, donor_id, distance, match_status, created_at conversations id, request_id, created_at, status messages id, conversation_id, sender_id, message, message_type, created_at, read_at verification_records id, user_id, cnic_document_url, selfie_url, verification_status, reviewed_by, reviewed_at, rejection_reason, created_at notifications id, user_id, title, body, type, reference_id, is_read, created_at device_tokens id, user_id, fcm_token, platform, created_at, updated_at Supabase Auth should remain the source of truth for authentication credentials. Sensitive health information should have stricter access policies. 6. Authentication Supabase Auth should manage authentication. Recommended methods: Phone OTP Email/password Optional social login in a future version For the Pakistani target market, phone authentication should be prioritized. User │ ▼ Enter Phone │ ▼ Supabase Auth │ ▼ OTP Verification │ ▼ Authenticated Session │ ▼ Create / Retrieve Profile Authentication and authorization are separate. Authentication establishes who the user is; authorization determines what the user is allowed to do. Authorization should be enforced through PostgreSQL Row Level Security and backend functions. 7. Verification Architecture Verification is a critical security component because Donora+ claims to provide verified donors. The initial version should use manual admin verification rather than attempting to build a complicated automated identity-verification system. User │ ├── CNIC Photo └── Live Selfie │ ▼ Secure Upload │ ▼ Verification Record │ ▼ Admin Dashboard │ ┌────┴─────┐ ▼ ▼ Approved Rejected │ ▼ Verified Donor 8. Smart Matching System The matching engine should consider: Blood group compatibility Donor verification status Donor availability Donation cooldown Health eligibility Geographic proximity Account status Active donation requests User's city/region Blood Request Created │ ▼ Validate Request │ ▼ Find Verified Donors │ ▼ Filter Blood Compatibility │ ▼ Filter Donation Cooldown │ ▼ Filter Availability │ ▼ Calculate Distance │ ▼ Rank Candidates │ ▼ Notify Suitable Donors Matching logic must run server-side. The mobile application should never determine final medical eligibility using client-side code alone. 9. Location and Map Architecture Google Maps Platform can be used for map rendering, location visualization and geocoding. The system should avoid exposing exact donor coordinates unnecessarily. Database: Donor coordinates → stored securely Matching engine: Coordinates → used for distance calculation Seeker: Approximate donor location → displayed on map Exact donor location should only be shared when appropriate and authorized. 10. Real-Time Chat Supabase Realtime can support the initial chat system. Donor │ ▼ Flutter App │ ▼ Supabase │ ▼ PostgreSQL messages │ ▼ Supabase Realtime │ ▼ Seeker Flutter App Realtime can support: New messages Message read status Request status Donation status updates 11. Push Notification Architecture Firebase Cloud Messaging should handle mobile push notifications. Blood Request │ ▼ Matching Edge Function │ ▼ Eligible Donors │ ▼ FCM Device Tokens │ ▼ Firebase Cloud Messaging │ ▼ Donor Mobile Devices Notification types can include: New nearby blood request Urgent blood request New chat message Match accepted Verification approved/rejected Request cancelled Donation reminder Sensitive medical information should not be unnecessarily included in push notification text. 12. AI Chatbot Architecture Alibaba Cloud AI can power the in-app chatbot. The chatbot should not be called directly from Flutter using a secret API key. Flutter │ ▼ Supabase Edge Function │ ├── Authentication check ├── Rate limiting ├── Input validation └── Context filtering │ ▼ Alibaba Cloud AI │ ▼ Edge Function │ ▼ Flutter The chatbot can provide general informational guidance about: Donation eligibility Preparation Basic blood donation information App usage Frequently asked questions It should not diagnose medical conditions or make definitive medical decisions. Medical questions requiring professional judgment should be directed to an appropriate healthcare professional. 13. API Architecture Donora+ can primarily use Supabase client APIs, PostgreSQL operations protected by RLS, Supabase Edge Functions, Firebase FCM, Google Maps APIs and Alibaba Cloud AI APIs. Function / Endpoint Purpose create-blood-request Create and validate request find-matches Generate donor matches send-notification Trigger FCM notification submit-verification Submit verification request admin-review-verification Approve/reject verification chatbot Secure AI gateway update-donation-status Update donation lifecycle calculate-eligibility Server-side eligibility logic Not every database operation needs a custom endpoint. Simple CRUD operations can use Supabase APIs with appropriate RLS policies. 14. Storage Architecture Recommended Supabase Storage buckets: profile-images verification-documents verification-selfies chat-attachments Profile images can be public or controlled depending on product requirements. CNIC documents and verification selfies must remain private. Temporary signed URLs can be used for authorized administrative review. 15. Security Architecture 15.1 Database Security Users can update their own profile. Users can read their own verification status. Users can only access conversations they participate in. Seekers cannot modify donor verification status. Donors cannot approve themselves. Only authorized administrators can review verification records. 15.2 API Security Validate authentication. Verify authorization. Validate request parameters. Apply rate limiting where necessary. Perform the operation server-side. Log important security events. 15.3 Sensitive Data Encrypt data in transit using HTTPS. Keep sensitive files private. Do not expose storage bucket URLs publicly. Use signed URLs. Restrict administrative access. Maintain verification audit logs. Avoid storing unnecessary personal information. 16. Admin Dashboard Recommended stack: Next.js + TypeScript. Main modules: Admin Dashboard │ ├── Overview ├── User Management ├── Donor Verification ├── Blood Requests ├── Reports ├── User Reports / Abuse ├── Notifications ├── Audit Logs └── System Settings If the team grows, administrative permissions can be separated into Super Admin, Verification Admin, Support Admin and Moderator roles. 17. Data Flow 17.1 User Registration User → Flutter → Supabase Auth → Authentication Session → Create Profile → PostgreSQL 17.2 Donor Verification Donor → CNIC + Selfie → Supabase Storage → Verification Record → Admin Dashboard → Review → Verification Status → Donor Profile 17.3 Blood Request Seeker → Create Request → Validate → PostgreSQL → Matching Function → Eligible Donors → FCM → Donor 17.4 Chat Seeker → Send Message → Supabase → PostgreSQL → Realtime Event → Donor 18. Donation Lifecycle Request Created │ ▼ Matching │ ▼ Donor Notified │ ▼ Donor Accepts │ ▼ Connection / Chat │ ▼ Donation Arranged │ ▼ Donation Completed │ ▼ Cooldown Applied A defined state machine prevents ambiguous states and simplifies maintenance. 19. Deployment Architecture Mobile: Google Play Store Apple App Store Backend: Supabase PostgreSQL Supabase Auth Supabase Storage Supabase Realtime Supabase Edge Functions Admin Dashboard: Next.js deployment using a platform such as Vercel GitHub │ ├── Flutter Repository └── Admin Dashboard Repository │ ▼ CI/CD │ ▼ Vercel Production secrets must be stored in environment variables and never committed to Git. 20. Environment Strategy Development │ ▼ Staging │ ▼ Production At minimum, maintain separate Supabase projects for development and production so testing cannot accidentally modify production data. 21. Monitoring and Logging Recommended monitoring: Sentry for Flutter crashes, API errors and runtime exceptions. Supabase monitoring for database performance, Edge Function failures, authentication failures, storage usage and Realtime connections. Useful non-sensitive operational metrics include: Registered users Verified donors Active donors Blood requests Successful matches Request response rate Average matching time Notification delivery rate Chat activity Do not log CNIC numbers, private messages or unnecessary health information. 22. Scalability Strategy Donora+ does not need a complex microservices architecture at launch. The recommended approach is to start with Flutter + Supabase + FCM + Google Maps + Alibaba Cloud AI + Next.js. 22.1 Stage 1 — MVP Flutter Supabase FCM Google Maps Alibaba Cloud AI Next.js Admin Dashboard 22.2 Stage 2 — Growth Database indexes Improved matching queries Background jobs Caching More detailed monitoring Rate limiting Search optimization 22.3 Stage 3 — Large Scale Dedicated matching service Redis caching Message queue Dedicated backend services Read replicas Advanced geospatial infrastructure These components should only be introduced when actual scale or performance requirements justify them. 23. Database Optimization Important PostgreSQL indexes should include: profiles.user_id donor_profiles.blood_group donor_profiles.city donor_profiles.availability_status donor_profiles.last_donation_date blood_requests.status blood_requests.blood_group blood_requests.created_at matches.request_id matches.donor_id messages.conversation_id notifications.user_id For location-based matching, PostgreSQL geospatial capabilities can be introduced when the basic latitude/longitude approach becomes insufficient. 24. Reliability and Failure Handling Network failure Notification failure Expired blood requests Donor becoming unavailable Verification rejection Duplicate requests Duplicate notifications Chat delivery failure Backend service downtime If an FCM notification fails, the blood request must still exist in the database. Notifications are a delivery mechanism, not the source of truth. 25. Privacy Considerations Donora+ should follow the principle of minimum necessary data. The application should collect only information required for authentication, donor verification, matching, communication, safety and administration. Seeker ↓ Approximate donor location ↓ Verified donor profile ↓ Match accepted ↓ Communication Avoid exposing exact home addresses, CNIC information, private health records or verification documents. 26. Recommended Project Architecture Mobile application: Presentation │ ▼ State Management │ ▼ Repository Layer │ ▼ Supabase / API Services Backend: Flutter Client │ ▼ Supabase APIs │ ├── PostgreSQL ├── Storage ├── Realtime └── Edge Functions │ ├── FCM ├── Google Maps └── Alibaba Cloud AI 27. Key Security Rules Never store passwords manually. Never put API secrets in Flutter code. Never expose the Supabase service-role key in the mobile application. Never make CNIC storage publicly accessible. Never rely exclusively on frontend authorization. Never allow users to mark themselves as verified. Never let the client determine final donor eligibility. Never expose exact donor locations unnecessarily. Never log CNIC numbers or sensitive health information. Use RLS for all user-facing database tables. Validate all privileged operations server-side. Maintain an audit trail for administrative actions. 28. Final Technology Recommendation For the initial production version, the architecture should be kept to these core technologies: Category Technology Frontend Flutter, Dart, Riverpod Backend Supabase, PostgreSQL, Edge Functions, Realtime, Storage, Auth External Services Firebase Cloud Messaging, Google Maps Platform, Alibaba Cloud AI Administration Next.js, TypeScript Engineering Git, GitHub, GitHub Actions, Sentry This architecture provides Donora+ with authentication, verified donor management, blood-request matching, realtime communication, push notifications, AI assistance, secure document storage and administrative moderation without the operational complexity of a large microservices platform. The central architectural principle is to keep identity verification, donor eligibility, matching decisions, authorization and sensitive-data access on the backend, while keeping Flutter responsible primarily for presentation and user interaction. This gives Donora+ a practical MVP architecture that can grow into a larger platform without requiring a complete rewrite.
